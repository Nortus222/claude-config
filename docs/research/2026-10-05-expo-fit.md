# Expo fit for the agent configuration manager

Researched 2026-10-05 against current official Expo and React Native documentation. No dependencies installed, scaffolding, runtime tests, or benchmarks performed.

## Recommendation

**Expo is a good candidate for a mobile companion or a deliberately universal mobile/web UI. It does not replace the desktop shell and installation engine this project needs.** For the current desktop-first product, keep the TypeScript/Effect backend separate and prefer a browser dashboard in Electron or Tauri. Reconsider Expo if mobile becomes a committed near-term requirement and sharing screens matters more than desktop-specific UI freedom.

Expo's main documented universal targets are **Android, iOS, and web**. EAS Build produces Android and iOS binaries; its macOS/Linux build hosts are not native desktop application targets. React Native macOS and Windows exist, but React Native classifies them as partner-maintained **out-of-tree** platforms. Linux has community routes such as React Native Skia. This makes native desktop possible, with additional integration and per-package compatibility work rather than one first-party Expo pipeline covering our three desktop operating systems. [Expo targets](https://docs.expo.dev/), [EAS Build](https://docs.expo.dev/build/introduction/), [React Native platforms](https://reactnative.dev/docs/out-of-tree-platforms).

## What Expo could provide

Expo offers TypeScript/React, file-based navigation, deep links, mobile tooling, and a web export. React Native Web wraps React DOM primitives, and Expo also explicitly supports web-only DOM components. It can therefore serve the public profile site and reusable mobile screens; choosing Expo does not force every screen to use native primitives. [Expo Router](https://docs.expo.dev/router/introduction/), [web support](https://docs.expo.dev/workflow/web/).

An exported Expo web UI could be hosted in Electron's renderer or Tauri's webview. This is an architectural inference from Expo's browser export, not an integration tested here. We would still need the desktop shell, IPC adapter, local engine, credentials integration, and signed desktop release pipeline. Metro/Expo would replace the renderer's Vite build, not the privileged backend. Dense settings tables, diffs, keyboard interaction, and desktop editors should be evaluated before adopting a shared native UI vocabulary.

## Runtime and local operations

Expo native apps normally run JavaScript on **Hermes**, not Node. Installing Node to develop an Expo application does not provide Node filesystem or subprocess APIs inside its native runtime. Expo's Metro docs separately distinguish Node server bundles from browser bundles, where Node built-ins can become empty shims. Our existing `.mjs` installation code should therefore stay in a real Node/Bun host, accessed through validated operations. The TypeScript/Effect requirement remains intact; the UI's JavaScript engine does not determine the backend runtime. [Hermes](https://docs.expo.dev/guides/using-hermes/), [Metro Node built-ins](https://docs.expo.dev/versions/latest/config/metro/#nodejs-built-ins).

It would be incorrect to say Expo cannot access files or native capabilities. Expo supplies filesystem APIs and supports custom native code through development builds and modules. **Expo Go** is the limited environment: it cannot load arbitrary custom native libraries. Supporting desktop Git, installer subprocesses, and home-directory configuration would require compatible desktop modules or a separate service, plus operating-system permission handling. [FileSystem](https://docs.expo.dev/versions/latest/sdk/filesystem/), [custom native code](https://docs.expo.dev/workflow/customizing/).

## A useful future role

A mobile companion could browse profiles and edit shared preferences through repository APIs or an authenticated service. Reported machine state and remote update requests require communication with the desktop agent, which applies approved revisions locally. Reuse schema/contracts, pure profile logic, API clients, and suitable components; avoid forcing desktop installation workflows onto phones.

Expo's SecureStore documents mobile credential storage, so it should not be assumed to solve desktop token storage. EAS Update can deliver compatible JavaScript/assets, but native-code changes require a new binary; it also does not deploy the separate local backend or approve profile revisions. [SecureStore](https://docs.expo.dev/versions/latest/sdk/securestore/), [update compatibility](https://docs.expo.dev/eas-update/runtime-versions/).

Choose Expo now if mobile/web parity is an actual product requirement. Otherwise, a React DOM desktop/public-site UI keeps the initial architecture smaller, while a future Expo companion remains straightforward at the shared domain and API boundary.
