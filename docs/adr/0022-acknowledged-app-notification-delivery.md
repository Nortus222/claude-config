# App notifications require acknowledged posting

The headless agent cannot prove OS notification delivery from a socket write or a successful app launch. Protocol v3 therefore sends bounded notification payloads only to authenticated app subscribers, with a fresh runtime receipt bound to the selected connection and a deadline. A notify-only app fetches a durable payload and claims the active launch receipt without subscribing. Only that connection can acknowledge posting; refusal, disconnect or expiry permits fallback. Receipts are never durable dedup identities. The service records the host executable path only after successful app registration so hidden delivery uses the registered app identity without scanning installation locations. Persisting acknowledgment after OS posting leaves a crash window that can repeat a notification, which is preferable to permanently suppressing an undelivered batch.

The macOS host uses UserNotifications directly because delivery acknowledgment needs the native add-request completion and clicks need a retained delegate. The renderer only receives a Review & apply route and can consume a pending route after startup; it cannot submit payloads or acknowledgments. Hidden delivery resolves paths through a read-only helper before connecting without a subscription or window. Native work stops starting submissions after a three-second local budget, while connected receipts allow five seconds. OS acceptance before a lost or expired acknowledgment still leaves a possible duplicate window.
